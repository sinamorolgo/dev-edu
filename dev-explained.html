개발 용어를 외우게 하지 말고, 눈앞의 서비스가 어떤 부품으로 움직이는지 먼저 보여주세요. 아래 지도에서 한 칸씩 눌러보면 전체 흐름이 잡힙니다.

STEP 1

먼저 “무슨 문제를 푸는지” 정합니다.

개발은 코드를 쓰기 전에 시작됩니다. 사용자가 어떤 상황에서 무엇을 더 쉽게 해야 하는지 한 문장으로 정하면, 이후의 화면과 기능이 흔들리지 않습니다.

비개발자가 이해하면 좋은 것
  • 기능은 “있으면 좋은 것”보다 “누가 언제 왜 쓰는지”가 먼저입니다.
  • 좋은 요구사항은 사용자의 행동과 완료 조건이 보입니다.
  • 애매한 문장은 개발 중간에 비용으로 돌아옵니다.
예시로 바꾸면
전“예약 기능을 만들어 주세요.”
후“고객이 날짜와 시간을 고르면, 가능한 자리만 보여주고 예약 완료 문자를 받게 해주세요.”

버튼 하나를 바꾸면, 코드의 어느 부분이 바뀌는지 보입니다.

왼쪽 값을 바꾸면 오른쪽 서비스 화면과 코드가 함께 바뀝니다. 비개발자에게는 이 연결감이 첫 번째 이해의 문입니다.

다섯 단어만 알면 큰 그림이 보입니다.

처음에는 모든 기술명을 외울 필요가 없습니다. 비개발자에게는 각 부품이 맡는 역할을 구분하는 것이 훨씬 중요합니다.

HTML

페이지에 어떤 내용이 놓이는지 정하는 뼈대입니다.

CSS

색, 간격, 크기처럼 보기 좋고 읽기 좋게 만드는 규칙입니다.

JavaScript

버튼 클릭, 입력 확인, 화면 변경처럼 움직임을 담당합니다.

API

프론트와 서버가 정보를 주고받는 약속된 통로입니다.

DB

회원, 주문, 예약처럼 사라지면 안 되는 정보를 저장합니다.

개발 용어를 일상어로 번역합니다.

용어를 무서워하지 않게 만드는 가장 빠른 방법은 “그래서 내 서비스에서는 무슨 뜻인가요?”로 바꾸는 것입니다.

용어 번역

프론트엔드

사용자가 직접 보는 화면과 상호작용입니다. 버튼이 어디에 있고, 문구가 무엇이고, 클릭하면 화면이 어떻게 반응하는지가 여기에 속합니다.

일상어

가게의 매장, 메뉴판, 주문대

확인 질문

사용자가 어느 화면에서 무엇을 눌러야 하나요?

개발자에게는 “기능명”보다 “상황, 행동, 결과”가 잘 전달됩니다.

비개발자가 개발을 이해하면, 요구사항도 훨씬 선명해집니다. 아래 문장 구조를 그대로 쓰면 회의 시간이 줄어듭니다.

좋은 요청의 4칸
  1. 1
    사용자

    누가 쓰나요? 고객, 관리자, 파트너, 내부 운영자처럼 역할을 정합니다.

  2. 2
    상황

    언제 필요하나요? 결제 전, 로그인 후, 예약 변경 중처럼 맥락을 붙입니다.

  3. 3
    행동

    무엇을 해야 하나요? 선택한다, 입력한다, 확인한다, 취소한다처럼 동사로 말합니다.

  4. 4
    결과

    끝나면 무엇이 보여야 하나요? 저장, 알림, 다음 화면, 실패 메시지까지 적습니다.

바로 쓰는 문장
  1. A
    기본형

    “사용자가 [상황]에서 [행동]하면 [결과]가 되게 해주세요.”

  2. B
    예외형

    “만약 [조건]이면 [실패 메시지]를 보여주고, 다시 시도할 수 있어야 합니다.”

  3. C
    데이터형

    “완료되면 [저장할 정보]가 남아야 하고, [누가] 다시 볼 수 있어야 합니다.”

  4. D
    우선순위형

    “이번에는 [핵심 행동]까지가 필수이고, [보조 기능]은 다음 단계로 미룹니다.”

마지막으로 헷갈리는 부분만 확인합니다.
