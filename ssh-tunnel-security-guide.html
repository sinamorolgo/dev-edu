일곱 문장으로 다시 보기

  • Lightsail 방화벽은 누가 SSH 22 문 앞까지 오는지 정합니다.
  • SSH 키는 신원을 증명하고, 실제 권한은 서버 계정이 정합니다.
  • SSH 22를 전체 IPv4에 여는 것은 로그인 전체 공개나 DB 직접 공개와 다릅니다.
  • root 계정에 등록된 키는 서버 전체 피해로 이어질 수 있어 직접 root 로그인과 넓은 sudo를 피합니다.
  • 정배의 터널 계정은 no-shell, non-sudo, 지정 local forwarding 전용이어야 합니다.
  • LaunchAgent는 Mac 사용자 로그인 후 터널을 시작하고 재연결합니다.
  • age와 Wormhole로 개인키를 보호해 전달했어도 개인별 키·공개키 등록 방식이 더 안전합니다.

첫 번째 관문

“IP 제한”과 “키만 있으면 접근”은 서로 다른 정책입니다.

Lightsail 방화벽은 서버의 공개 IP로 들어오는 연결을 먼저 거릅니다. SSH 키 인증은 그 다음 단계에서 신원을 확인합니다.

질문 특정 공인 IP만 허용 SSH 22를 모든 IPv4에 허용
방화벽 규칙 203.0.113.10/32 → TCP 22 0.0.0.0/0 → TCP 22
문 앞까지 오는 사람 등록한 공인 IPv4 한 개 전 세계 IPv4 주소에서 접속 시도 가능
로그인 조건 IP 통과 후에도 승인된 개인키가 필요 여전히 승인된 개인키가 필요
장점 키가 새어도 출발 IP라는 두 번째 장벽이 남음 Wi-Fi·공인 IP가 바뀌어도 방화벽 재등록이 필요 없음
부담·위험 유동 IP가 바뀔 때 운영자가 갱신해야 함 스캔·로그인 시도·SSH 구현 공격에 노출되는 면이 넓어짐
필수 보완 키 전용 인증, root 차단, 계정 최소 권한 키 전용 인증, root 차단, 허용 사용자·목적지 제한, 모니터링을 더 엄격히

“다 연다”의 정확한 뜻

여기서 모든 것을 연다는 뜻은 아닙니다. SSH용 TCP 22번 포트의 출발지 제한만 모든 IPv4로 넓히는 것입니다. DB 5432, Redis 6379와 다른 포트까지 공개하는 설정이 아닙니다.

Lightsail에서 놓치기 쉬운 점

IPv4와 IPv6 방화벽은 별도입니다. 같은 22번 포트에 특정 IP 규칙과 전체 허용 규칙이 함께 있으면 더 개방적인 규칙이 이깁니다.

AWS는 SSH 22를 필요한 컴퓨터의 IP로 제한할 수 있다고 안내하고, 같은 포트에 여러 규칙이 있으면 가장 개방적인 규칙이 적용된다고 설명합니다. 공식 문서 보기

현재 상태와 정책안을 구분하세요. 작성 시점의 origin/master는 여전히 /32 허용 정책입니다. 0.0.0.0/0 → TCP 22로 바꾸는 스크립트는 로컬의 미커밋 변경이며, 실제 Lightsail 방화벽에 적용됐다고 확인된 상태는 아닙니다. 이 자료에서는 두 정책의 차이를 배우되, 운영 상태는 AWS에서 별도로 확인해야 합니다.

SSH 키는 신분증이고, 권한표는 서버 계정에 있습니다.

키 쌍은 누군지를 증명합니다. 무엇을 할 수 있는지는 공개키가 등록된 Linux 계정과 SSH 서버 정책이 결정합니다.

일반 사용자

자기 파일과 허용된 프로세스를 다룹니다. 필요한 관리 작업만 제한된 sudo로 올리는 방식이 좋습니다.

root

Linux 안에서 사실상 모든 권한을 가집니다. 작은 실수와 키 탈취의 피해 범위가 서버 전체가 됩니다.

Codex가 root SSH를 잡으면 무엇이 달라질까요?

Codex가 특별한 root 권한을 만들어 내는 것은 아닙니다. 하지만 사용자가 SSH와 명령 실행을 허용했고 원격 세션의 계정이 root라면, 서버는 Codex가 보낸 명령도 root 명령으로 처리합니다.

  • 모든 애플리케이션·설정·데이터 파일을 읽고 바꾸거나 삭제
  • DB·Redis·웹·worker 서비스를 멈추고 재시작하거나 제거
  • 사용자·SSH 키·권한·서버 방화벽 규칙을 변경
  • 서버의 비밀값과 고객 데이터를 읽거나 외부로 전송
  • 프로세스를 종료하고 OS를 재부팅·종료
  • 잘못된 삭제·디스크 작업으로 부팅 불능이나 광범위한 손실 유발

PermitRootLogin no만으로 끝나지 않습니다.

일반 계정에 무제한 passwordless sudo가 있으면 사실상 root와 비슷합니다. 직접 root 로그인 차단과 함께 sudo 범위도 최소화해야 합니다.

SSH만으로 AWS 리소스까지 지워지지는 않습니다.

root는 서버 OS를 끄고 망가뜨릴 수 있지만, Lightsail 인스턴스 자체 삭제나 AWS 콘솔 방화벽 변경에는 별도의 AWS API 자격증명과 권한이 필요합니다. 서버 안에 그런 자격증명이 있다면 위험 범위가 다시 넓어집니다.

OpenSSH는 PermitRootLogin no, local forwarding만 허용하는 AllowTcpForwarding local, 목적지를 제한하는 PermitOpen을 제공합니다. sshd_config 매뉴얼 · Codex의 로컬 명령 실행 범위는 sandbox와 approval 설정에 의해 제어됩니다. OpenAI Docs

정배 Mac의 현재 목적

터널링은 “내 Mac의 로컬 문”을 서버 안쪽 서비스에 잇는 일입니다.

PostgreSQL과 Redis를 인터넷에 직접 공개하지 않습니다. 대신 정배 Mac의 127.0.0.1 포트로 들어온 연결만 SSH 암호화 통로를 지나 서버의 loopback 서비스로 전달합니다.

정배 Mac

127.0.0.1은 “이 Mac 자신”입니다.

PostgreSQL 입구25432
Redis 입구26379
SSH local forwarding공개 TCP 22를 지나는 암호화된 통로

Lightsail 서버

여기서 127.0.0.1은 “서버 자신”입니다.

PostgreSQL5432
Redis6379
ssh -N -T \
  -L 127.0.0.1:25432:127.0.0.1:5432 \
  -L 127.0.0.1:26379:127.0.0.1:6379 \
  tunnel-user@server

-L은 local forwarding

내 Mac 주소:내 포트:서버에서 볼 목적지:목적지 포트 순서입니다. -N은 원격 명령을 실행하지 않고 포워딩만 하겠다는 뜻이고, -T는 터미널 화면을 할당하지 않습니다.

로컬 주소를 명시하는 이유

127.0.0.1에 묶으면 같은 Mac의 프로그램만 그 입구를 사용합니다. 빈 주소나 모든 인터페이스에 바인딩하면 같은 네트워크의 다른 기기까지 접근할 수 있어 의도치 않은 재공개가 될 수 있습니다.

터널은 운반 통로일 뿐입니다. 터널 연결에 성공해도 PostgreSQL 사용자·비밀번호와 Redis 인증 같은 서비스 자체의 인증은 여전히 별개로 필요합니다. 터널이 DB 권한을 자동으로 주지는 않습니다.

“DB·Redis만 쓴다”는 목적과 실제 허용 범위는 따로 확인해야 합니다.

말로 정한 사용 목적과 기술적으로 가능한 범위가 일치해야 최소 권한이 됩니다.

정배 Mac의 업무 목적

  • 로컬 API가 shared PostgreSQL·Redis 사용
  • Mac에서는 worker를 실행하지 않음
  • SSH 셸·sudo·임의 서버 명령은 필요 없음

현재 확인한 helper의 허용 범위

  • DB 25432, Redis 26379
  • 통합 확인용 API·관리자·고객 웹 23100·23200·23300도 함께 포워딩
  • 그래도 개발자 계정은 no-shell, non-sudo, 지정 목적지 전용

판단 기준: 업무상 정말 DB·Redis 두 목적지만 필요하다면 SSH 서버의 PermitOpen, 개인키의 authorized_keys 제한, Mac의 LaunchAgent 포워드 목록까지 두 서비스만 남아야 “기술적으로도 DB·Redis 전용”이라고 말할 수 있습니다.

운영 권한도 분리합니다. 정배 Mac은 AWS CLI·운영자 자격증명·관리자 키를 받지 않습니다. 애플리케이션 연결에 필요한 별도 profile만 비공개로 받아 macOS Keychain에 보관하며, SSH 인증과 DB·Redis 인증은 서로 다른 경계로 유지합니다.

LaunchAgent는 로그인 후 터널을 켜고, 끊기면 다시 붙입니다.

“맥북 전원을 켜면 자동”이라고 줄여 말하지만, 사용자용 LaunchAgent는 정확히는 그 사용자가 macOS에 로그인한 뒤 실행됩니다.

Apple은 ~/Library/LaunchAgents를 로그인한 사용자에게만 적용되는 agent 위치로 설명합니다. launchd로 스크립트 관리

LaunchAgent에 개인키 내용을 넣지 않습니다. 개인키 파일은 보통 ~/.ssh에 두고 소유자만 읽도록 보호합니다. LaunchAgent는 그 키의 경로와 터널 실행 방법을 가리키며, passphrase 사용 시 macOS Keychain·SSH agent가 잠금 해제를 도울 수 있습니다.

친구와 운영자가 같은 개인키를 가지면 누가 접속했는지 구분하기 어렵고, 친구 한 명만 접근 해제하기도 어렵습니다. 한 복사본이 새면 같은 신분 전체가 위험합니다.

다음부터는 개인키를 보내지 않는 흐름이 더 안전합니다.

공개키는 배포해도 되는 승인표 재료이고, 개인키는 친구 Mac에서 한 번도 나오지 않아야 합니다.

1. 친구가 생성

친구 Mac에서 친구 전용 SSH 키 쌍을 만듭니다.

2. 공개키만 전달

.pub 한 줄과 fingerprint만 운영자에게 보냅니다.

3. 제한 계정에 등록

운영자가 no-shell, non-sudo, 지정 포워딩 전용 계정에 공개키를 등록합니다.

4. 개인별 폐기

접근을 끊을 때 그 친구 공개키만 제거하면 다른 사람 키는 유지됩니다.

이미 개인키를 공유했다면: 친구가 새 개인 키 쌍을 만들고 새 공개키로 접속을 검증한 뒤, 서버 승인 목록에서 공유했던 이전 공개키를 제거하는 방향으로 교체합니다. 그 키의 공개키가 root·관리자 계정에 등록돼 있었다면 더 긴급하게 별도 개인 키와 제한 계정으로 바꿔야 합니다.

age 공식 문서는 recipient 공개키 암호화와 SSH 공개키 지원을 설명합니다. Magic Wormhole 공식 문서는 일회용 코드, PAKE, 직접 연결과 암호화 relay를 설명합니다.

상황을 만나면 이 순서로 판단하세요.

“키가 있으니 안전하다”에서 멈추지 말고, 다섯 관문을 차례로 확인합니다.

확인 순서 질문 정배 터널에서 바람직한 답
1. 도달성 어느 IP가 TCP 22에 도달하는가? 정책에 따라 /32 또는 전체 IPv4. 다른 포트는 공개하지 않음.
2. 인증 비밀번호도 허용하는가? 개인별 공개키 인증만 허용.
3. 계정 root나 sudo가 가능한가? 아니요. 개인별 non-sudo 터널 계정.
4. 세션 셸, TTY, agent·reverse forwarding이 가능한가? 아니요. local forwarding만 허용.
5. 목적지 임의의 서버·포트로 전달할 수 있는가? 현재 helper는 loopback의 앱 3개와 DB·Redis, 총 5개 지정 목적지만 허용. DB·Redis 전용으로 줄이려면 세 계층의 목록을 함께 축소.
6. 자동화 터널을 누가 언제 유지하는가? 사용자 로그인 후 LaunchAgent가 시작·재연결.
7. 폐기 친구 한 명만 따로 접근 해제할 수 있는가? 개인별 공개키와 서버 계정이라 가능.

방화벽은 도달성을, 키는 신원을, 계정과 SSH 정책은 권한을 정합니다.
