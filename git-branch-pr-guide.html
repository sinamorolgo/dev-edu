Git 브랜치와 PR

비개발자도 실무 대화가 가능해지는 Git 입문

브랜치는 내 작업 책상, PR은 팀에게 보내는 검토 요청입니다.

Git을 처음 배울 때 가장 어려운 부분은 명령어가 아니라 “내 컴퓨터, 원격 저장소, 팀 검토”가 서로 다른 장소라는 점입니다. 이 페이지는 그 장소의 차이를 눈으로 먼저 잡고, 실무 순서로 연결합니다.

브랜치는 main을 망치지 않는 개인 작업 공간입니다.

팀이 쓰는 안정된 길이 main이라면, 브랜치는 그 옆에 잠깐 만든 작업 길입니다. 새 기능, 수정, 실험은 브랜치에서 하고 검토가 끝나면 main으로 합칩니다.

git switch -c feature/login-copy
핵심 감각: 브랜치를 만든다고 파일이 복사되어 두 벌 생기는 느낌보다, 같은 기록에서 갈라진 새 작업 흐름이 생긴다고 이해하면 좋습니다.
기억: 브랜치 = 따로 일하는 길.
질문: 지금 내 브랜치인가요?

commit, push, PR은 같은 “올리기”가 아닙니다.

처음에는 세 단어가 모두 저장처럼 들립니다. 하지만 저장되는 장소와 팀에게 보이는 정도가 다릅니다.

1. 어디에 있나요?

내 컴퓨터라면 commit, 원격 저장소라면 push 이후입니다.

2. 누가 볼 수 있나요?

push 전에는 보통 나만 보고, push 후에는 팀이 브랜치를 볼 수 있습니다.

3. 합쳐도 되나요?

PR은 main에 합치기 전, 팀이 검토하는 대화 공간입니다.

PR이 아직 열리지 않았습니다.

draft main

브랜치를 푸시한 뒤 PR을 열면, 이곳에 리뷰어가 볼 설명이 만들어집니다.

체크: 변경 요약, 테스트 여부, 확인이 필요한 화면

좋은 PR은 코드보다 먼저 맥락을 전달합니다.

PR은 “제가 코드를 올렸어요”가 아니라 “이 변경을 main에 합쳐도 되는지 검토해주세요”라는 실무 커뮤니케이션입니다.

1

문제

왜 이 변경이 필요한지 먼저 말합니다.

2

변경

무엇이 바뀌었는지 범위를 좁힙니다.

3

확인

어떻게 확인했는지 재현 가능하게 적습니다.

4

요청

리뷰어가 봐야 할 지점을 명확히 남깁니다.

변경 목적

왜 바꿨는지 한 문장으로 보이면 리뷰어가 코드를 읽는 방향을 잡을 수 있습니다.

변경 범위

어떤 화면, 파일, 기능이 바뀌었는지 좁게 적으면 불필요한 추측이 줄어듭니다.

확인 방법

직접 눌러본 경로, 테스트 명령, 스크린샷을 적으면 리뷰 속도가 빨라집니다.

PR 설명 템플릿

## 무엇을 바꿨나요?
- 로그인 안내 문구를 더 명확하게 수정했습니다.

## 왜 바꿨나요?
- 사용자가 비밀번호 재설정 위치를 헷갈린다는 피드백이 있었습니다.

## 어떻게 확인했나요?
- 로그인 화면에서 문구 노출을 확인했습니다.
- 모바일 폭에서도 줄바꿈을 확인했습니다.

리뷰 요청 문장

이번 PR은 기능 추가보다 문구 개선이 핵심입니다.
특히 로그인 실패 시 사용자가 다음 행동을 이해할 수 있는지 봐주세요.

확인 부탁드릴 부분:
- 문구가 너무 길지 않은지
- 모바일 화면에서 버튼을 가리지 않는지

마지막으로 실무 판단만 확인합니다.

정답을 외우기보다 “지금 내 작업은 어디에 있는가?”를 구분하는 감각이 중요합니다.
