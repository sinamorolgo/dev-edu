왜 툴이 필요할까

언어 모델은 말을 이해하고 정리하는 데 강하지만, 우리 회사 DB의 오늘 설치 일정이나 체크리스트 상태를 스스로 알고 있지는 않습니다.

모델만 있으면 생기는 문제

모델은 그럴듯한 문장을 만들 수 있지만, 지금 DB에 있는 최신 설치 건수는 직접 알 수 없습니다. 그래서 업무 질문을 받으면 실제 시스템에 확인하는 통로가 필요합니다.

툴이 해결하는 문제

툴은 모델이 “이 질문은 설치일정 조회 버튼을 눌러야 한다”고 판단하게 해 줍니다. 버튼을 누르면 서버가 DB에서 최신 값을 가져오고, 모델은 그 결과를 사람이 읽기 쉬운 말로 바꿉니다.

세 사람이 같이 일하는 구조

원써치 AI Chat은 한 명이 모든 일을 하는 구조가 아닙니다. 말하는 사람, 판단하는 사람, 실제 업무 시스템을 움직이는 사람이 나뉘어 있습니다.

사용자 “오늘 설치 브리핑해줘”처럼 업무 언어로 요청합니다.

원써치 서버 허용된 함수만 실행하고 DB 결과를 다시 모델에게 돌려줍니다.

API와 툴은 어떻게 다를까

둘 다 서버 기능과 연결되지만, 누구를 위한 입구인지가 다릅니다.

구분 쉽게 말하면 원써치 AI Chat에서 하는 일
API 화면이나 다른 프로그램이 서버에 요청하는 공식 접수창입니다. ChatKit 화면이 `/chatkit` 접수창으로 사용자 메시지를 보냅니다.
툴 모델이 필요할 때 서버에 부탁할 수 있는 업무용 버튼입니다. 모델이 “설치 브리핑 조회 버튼을 눌러야겠다”고 선택하면 서버 함수가 실행됩니다.
도구 등록 모델에게 “이 버튼들은 눌러도 된다”고 메뉴판을 보여 주는 일입니다. Agent의 도구 목록에 설치일정, 고객조회, 체크리스트 같은 함수들을 넣습니다.

구조 지도로 보기

파일명을 외우는 것보다 층을 이해하는 것이 먼저입니다. 원써치 AI Chat은 아래 네 층으로 나누어 보면 쉽습니다.

화면 층 ChatKit 화면이 메시지, 모델 선택, 첨부파일, 응답 스트리밍 표시를 담당합니다.
API 층 화면에서 온 메시지를 받는 접수창입니다. 모델 목록과 첨부파일 업로드 접수창도 이 층에 있습니다.
대화 실행 층 최근 대화를 불러오고, 모델과 도구 실행을 이어 주며, 결과를 스트리밍으로 화면에 돌려보냅니다.
도구 등록 층 모델에게 보여 줄 도구 메뉴판을 만듭니다. 어떤 도구를 쓸 수 있고 어떤 모델을 쓸 수 있는지 정합니다.
업무 함수 층 설치일정 조회, 고객 계약 조회, 체크리스트 생성, 접수 대조, 통계 분석 같은 실제 업무를 수행합니다.

도구 등록은 어떤 식으로 될까

비개발자 관점에서는 “서버 함수 만들기 → 모델에게 보여 줄 메뉴에 넣기 → 언제 쓸지 설명하기” 세 단계로 이해하면 됩니다.

1. 업무 함수를 만든다

예를 들어 “오늘 설치 브리핑을 가져오는 함수”를 서버에 만듭니다. 이 함수는 날짜를 받아 DB에서 설치 예정 건을 조회합니다.

2. 도구로 감싼다

이 함수에 “모델이 호출할 수 있는 도구”라는 표시를 붙입니다. 함수 이름, 입력값, 설명이 모델에게 보이는 도구 설명이 됩니다.

3. 메뉴에 넣는다

Agent의 도구 목록에 넣어야 실제로 모델이 고를 수 있습니다. 함수만 만들어 두고 메뉴에 넣지 않으면 모델은 그 도구를 모릅니다.

최소 코드 느낌 `@function_tool` 표시가 붙은 서버 함수가 Agent의 도구 목록에 들어가면 모델이 호출할 수 있는 버튼이 됩니다.
도구 설명 “오늘/내일/이번 주 설치 예정 건을 브리핑할 때 사용”처럼 언제 쓰는지 설명해야 모델이 올바르게 고릅니다.
입력값 “오늘” 같은 말은 도구 입력값으로 바뀝니다. 원써치에서는 `today`, `tomorrow`, `week` 같은 값으로 처리합니다.

먼저 알아야 할 말들

AI Chat 코드를 읽기 전에 모델, API, Agent, Runner, Tool을 일상 언어로 잡아 두면 코드가 훨씬 덜 낯설어집니다.

용어 쉬운 뜻 원써치 코드에서 보면
모델 사용자 말을 이해하고 다음 행동이나 답변을 고르는 AI 두뇌입니다. gpt-5.5처럼 선택 가능한 모델 ID가 있고, 백엔드 allowlist가 임의 모델 사용을 막습니다.
API 화면이 서버에 “이 요청 처리해 주세요”라고 보내는 접수창입니다. ChatKit 화면은 /chatkit, 모델 목록은 /chatkit/models, 첨부파일은 /chatkit/attachments/upload로 보냅니다.
Agent 모델, 운영 지침, 설정, 도구 목록을 한 묶음으로 만든 실행 단위입니다. OneSearch DB Assistant Agent가 설치일정, 고객조회, 체크리스트 도구를 들고 실행됩니다.
Runner 모델에게 물어보고, 도구 호출이 나오면 실행하고, 결과를 다시 모델에게 넣는 진행자입니다. Runner.run_streamed(...)가 스트리밍 응답과 도구 실행 루프를 시작합니다.
Tool 모델이 직접 실행하지 않고 “서버야 이 함수 실행해 줘”라고 요청할 수 있는 업무 버튼입니다. @function_tool이 붙고 Agent의 tools 목록에 들어간 함수가 도구가 됩니다.

원써치 코드로 흐름 읽기

아래 스니펫은 실제 구조를 학습용으로 줄인 것입니다. 핵심은 “프론트가 API로 보냄 → 백엔드가 Agent를 만듦 → Runner가 모델과 도구 실행을 이어 줌 → 도구 함수가 DB 작업을 함”입니다.

1. 프론트: ChatKit 화면은 백엔드 접수창을 알고 있어야 한다 관리자 AI Chat 화면은 사용자가 입력한 메시지를 ChatKit 컴포넌트에 맡기고, ChatKit은 지정된 URL로 요청을 보냅니다. 
const _getChatKitApiUrl = () => {
  // 운영 환경에서 직접 endpoint를 지정할 수 있게 열어 둔 값입니다.
  const explicit = import.meta.env.VITE_DB_CHATBOT_API_URL;
  if (explicit) return explicit;

  // 기본은 원써치 메인 백엔드의 /chatkit 접수창입니다.
  return `${_stripTrailingSlash(API_BASE_URL)}/chatkit`;
};

const { control, ref: chatkitRef } = useChatKit({
  api: {
    url: _getChatKitApiUrl(),
    domainKey,
    uploadStrategy: {
      type: "direct",
      uploadUrl: `${_getChatKitApiUrl()}/attachments/upload`,
    },
  },
  composer: {
    // 모델 선택 UI와 첨부파일 제한도 여기서 설정합니다.
    models: modelOptions.length ? modelOptions : undefined,
    attachments: { enabled: true, maxSize: 24 * 1024 * 1024, maxCount: 2 },
    placeholder: "예) 오늘 설치일정 / 체크리스트 생성 / 남은 할일",
  },
});
  • 읽는 포인트: 프론트는 DB를 직접 조회하지 않습니다. 채팅 메시지를 백엔드 API로 보내는 역할입니다.
  • 모델 목록: 프론트는 /chatkit/models에서 받은 allowlist만 모델 선택 UI에 보여 줍니다.
  • 첨부파일: 파일도 채팅 본문에 그냥 붙는 것이 아니라 별도 업로드 API를 통해 attachment ID로 연결됩니다.
1-1. 모델: 프론트가 고른 모델도 백엔드가 다시 확인한다 모델은 AI 두뇌입니다. 원써치는 아무 모델명이나 실행하지 않고, 코드에 적힌 allowlist 안에서만 선택되게 합니다. 
DB_CHATBOT_DEFAULT_MODEL = "gpt-5.5"

DB_CHATBOT_MODEL_IDS = [
    "gpt-5.5",
    "gpt-5.4",
    "gpt-5.3-codex",
    "gpt-5-nano",
    "gpt-4o",
]

# 프론트 모델 선택 UI와 백엔드 검증이 같은 목록을 봅니다.
DB_CHATBOT_MODEL_OPTIONS = _build_model_options(
    DB_CHATBOT_MODEL_IDS,
    default_model=DB_CHATBOT_DEFAULT_MODEL,
)

DB_CHATBOT_ALLOWED_MODELS = {
    model["id"] for model in DB_CHATBOT_MODEL_OPTIONS if model.get("id")
}

def _pick_model_from_chatkit(input_user_message):
    model = input_user_message.inference_options.model

    # 프론트가 보낸 값이라도 allowlist 밖이면 사용하지 않습니다.
    if model not in DB_CHATBOT_ALLOWED_MODELS:
        return None

    return model
  • 읽는 포인트: 모델 선택은 UI 편의 기능이지만, 보안 판단은 백엔드가 다시 합니다.
  • 기본 모델: 사용자가 모델을 안 고르거나 잘못된 값을 보내면 기본 모델로 돌아갑니다.
  • 개발 판단: 모델을 늘릴 때는 비용, 추론 능력, reasoning 옵션 지원 여부, 내부 정책을 같이 봐야 합니다.
2. API: /chatkit은 메시지를 받고 실행 문맥을 만든다 백엔드 접수창은 요청 본문을 읽고, Prompt Studio 지침과 FastAPI app을 context에 담아 ChatKit 서버로 넘깁니다. 
@router.post("/chatkit")
async def chatkit_endpoint(request: Request):
    # ChatKit이 보낸 원본 요청입니다. 스레드, 메시지, 모델 선택 정보가 들어 있습니다.
    body = await request.body()

    # 운영 지침을 DB Prompt Studio에서 읽고, 실패하면 기본 지침으로 돌아갑니다.
    prompt = await load_db_assistant_instructions()

    # 도구가 FastAPI app, 사용자, 프롬프트 정보에 접근할 수 있게 문맥을 만듭니다.
    ctx = RequestContext(
        app=request.app,
        user_id="debug",
        db_assistant_prompt=prompt,
    )

    # 실제 ChatKit 프로토콜 처리는 DBChatKitServer가 맡습니다.
    result = await db_chatkit_server.process(body, context=ctx)

    if isinstance(result, StreamingResult):
        return StreamingResponse(result, media_type="text/event-stream")
  • 읽는 포인트: API는 모델에게 바로 묻지 않습니다. 먼저 운영 지침과 실행 문맥을 준비합니다.
  • RequestContext: 도구 함수의 ctx로 이어지는 내부 정보입니다. 사용자가 직접 입력하는 값이 아닙니다.
  • StreamingResponse: 답변을 한 번에 기다리지 않고, ChatKit 화면에 조금씩 흘려보내는 방식입니다.
2-1. 프롬프트: 운영 지침은 DB에서 읽고, 실패하면 기본값으로 돌아간다 도구 선택 품질은 모델만의 문제가 아닙니다. “언제 어떤 도구를 쓸지”를 알려 주는 운영 지침이 중요합니다. 
async def load_db_assistant_instructions(code: str | None = None):
    prompt_code = code or "db_chatkit.db_assistant.instructions"

    # 같은 프롬프트를 매 턴 DB에서 읽지 않도록 짧게 캐시합니다.
    ttl = _cache_ttl_seconds()
    cached = _CACHE.get(prompt_code)
    if ttl > 0 and cached and cached[0] > _now_ts():
        return cached[1]

    try:
        prompt_set = await repo.get_set_by_code(prompt_code)
        active = prompt_set.active_version
        part = _pick_part(active.parts, name="instructions")
        content = str((part or {}).get("content") or "").strip()

        if content:
            return PromptLoadResult(
                code=prompt_code,
                source="db",
                instructions=content,
            )

    except Exception:
        logger.warning("Prompt Studio load failed; using default instructions.")

    # Prompt Studio가 비어 있거나 장애가 나도 채팅 전체를 죽이지 않습니다.
    return PromptLoadResult(
        code=prompt_code,
        source="default",
        instructions=DEFAULT_INSTRUCTIONS,
    )

6. 안전장치: 읽기 전용 SQL도 실제 실행 전에 검문한다 “읽기 전용”이라는 이름만 믿지 않고, 실행 전에 문장 형태와 위험 키워드를 검사합니다. 
def _validate_readonly_sql(sql: str) -> str:
    q = _strip_sql_code_fence(sql)
    if not q:
        raise ValueError("SQL is empty.")

    # 한 번에 여러 SQL 문장을 실행하지 못하게 막습니다.
    if ";" in q.rstrip(";"):
        raise ValueError("Multiple statements are not allowed.")

    # SELECT 또는 WITH로 시작하는 조회만 허용합니다.
    if not re.match(r"^(select|with)\\b", q, re.IGNORECASE):
        raise ValueError("Only SELECT/WITH queries are allowed.")

    # UPDATE, DELETE, DROP 같은 위험 키워드를 막습니다.
    if _SQL_BAD_KEYWORDS.search(q):
        raise ValueError("Potentially unsafe SQL keyword detected.")

    # SELECT ... INTO는 테이블을 만들 수 있으므로 금지합니다.
    if re.search(r"\\binto\\b", q, re.IGNORECASE):
        raise ValueError("SELECT ... INTO is not allowed.")

    return q
  • 읽는 포인트: 모델이 만든 SQL은 신뢰하지 않고 서버가 다시 검사합니다.
  • 이중 안전: 코드 검사에 더해 Postgres에서는 read-only transaction과 statement timeout도 겁니다.
  • 운영 판단: 반복되는 업무 질문은 자유 SQL보다 전용 도구로 승격하는 편이 안전합니다.

D 현장 업무 설치일정, 고객 계약, 설치 브리핑, 체크리스트, 접수 대조, 남은 할일을 처리합니다.
E 분석/통계 렌탈사별, 지역별, 월별 통계와 데이터 이상 징후를 요약합니다.
F 쓰기 도구 체크리스트 생성이나 항목 상태 변경처럼 목적이 좁은 작업만 맡습니다.
G 첨부파일 현재 턴의 파일은 OpenAI file attachment로 변환하고, 오래된 첨부는 재전송하지 않습니다.

모델은 무엇을 보고 버튼을 고를까

모델은 서버 코드를 마음대로 뒤지는 것이 아닙니다. 서버가 건네준 도구 설명서와 운영 지침을 보고 판단합니다.

판단 재료 원써치에서의 역할 잘못 설계하면 생기는 문제
instructions “설치 몇 건?”은 설치 목록 조회, “브리핑”은 설치 브리핑 조회처럼 질문 의도와 도구를 연결합니다. 비슷한 도구가 많을 때 모델이 SQL을 먼저 쓰거나, 너무 넓은 도구를 고를 수 있습니다.
함수명 이름만 봐도 “접수 대기 조회”, “설치 통계 조회”처럼 목적이 드러나게 합니다. “데이터 처리”처럼 넓은 이름은 어떤 버튼인지 알기 어렵게 만듭니다.
docstring 사용 시점, 입력값 의미, 예시 질문을 모델에게 알려줍니다. 설명이 모호하면 사용자가 원하지 않은 도구가 호출될 수 있습니다.
입력값 형식 날짜 범위, 계약 ID, 카톡 복붙 내용처럼 모델이 채워야 할 값을 제한합니다. 필수값과 기본값이 부정확하면 tool 실패가 늘어납니다.
반환 결과 성공 여부, 목록, 건수, 오류 이유처럼 모델이 다시 설명할 수 있는 재료를 구조화합니다. 결과가 너무 크거나 불규칙하면 모델이 요약을 놓칩니다.

Prompt Studio와 기본 프롬프트

모델에게 “우리 회사에서는 이렇게 답하고, 이런 질문에는 이런 도구를 써라”라고 알려 주는 운영 설명서입니다.

운영 경로

서버는 Prompt Studio에서 활성화된 AI Chat 지침을 읽습니다. 운영자가 지침을 바꾸면 비교적 빠르게 새 대화에 반영됩니다.

fallback 경로

Prompt Studio를 읽지 못하면 코드에 들어 있는 기본 지침으로 돌아갑니다. 프롬프트 DB 문제 때문에 채팅 기능 전체가 바로 멈추지 않게 하는 장치입니다.

안전장치

툴 호출 구조의 핵심은 “모델이 알아서 무엇이든 한다”가 아니라, 허용된 함수와 허용된 입력 범위 안에서만 실행되게 만드는 것입니다.

SQL 도구 제한

자유 조회가 필요한 경우에도 읽기 전용만 허용합니다. 여러 문장, 삭제나 수정, 위험 함수, 너무 긴 쿼리는 막습니다.

모델 allowlist

화면에서 아무 모델 이름이나 보낼 수 없게 허용 목록을 둡니다. 백엔드도 같은 목록을 확인해 임의 모델 사용을 막습니다.

단계 제한

모델이 도구를 너무 오래 반복해서 부르지 않도록 최대 실행 단계를 둡니다. 복잡한 질문은 범위를 좁히라고 안내합니다.

첨부파일 제한

파일 크기와 개수를 제한하고, 오래된 첨부파일을 매번 다시 보내지 않아 비용과 입력 크기를 줄입니다.

쓰기 도구 분리

DB를 바꾸는 도구는 체크리스트 생성과 항목 상태 변경처럼 업무 목적이 좁게 정해져 있습니다. 일반 분석은 읽기 도구를 우선합니다.

Analytics 가드레일

Analytics Orchestrator는 쓰기 의도와 민감정보 대량 요청을 입력 가드레일로 막고, 최종 답변에는 metric 또는 fallback 근거가 들어가도록 출력 가드레일을 둡니다.

일반 DB Chat과 Analytics의 차이

일반 업무 질문은 바로 업무 버튼을 누르는 방식에 가깝고, Analytics는 여러 전문가에게 순서대로 일을 맡기는 방식에 가깝습니다.

이 경계를 놓치면 “AI가 DB를 직접 봤다”거나 “함수만 만들면 자동으로 된다”처럼 잘못 이해하기 쉽습니다.

맞는 이해

서버가 허용한 설치일정 도구를 메뉴에 등록하고, 운영 지침에 사용 기준을 적어 두면 모델이 설치일정 질문에서 그 도구를 요청할 수 있습니다.

틀린 이해

서버에 함수가 있다는 이유만으로 모델이 자동으로 찾아 쓰지는 않습니다. 도구 메뉴에 등록하고 설명까지 제공해야 모델이 선택할 수 있습니다.

새 AI Chat 툴을 만드는 절차

개발자가 새 기능을 AI Chat에 붙일 때는 “함수 하나 만들기”보다 “모델이 언제 고르고, 서버가 어디까지 실행하고, 실패하면 무엇을 돌려줄지”를 먼저 정해야 합니다.

1. 질문을 먼저 모은다

“어떤 사용자가 어떤 말로 물을까?”를 3개 이상 적습니다. 같은 데이터와 같은 결과 형식으로 답할 수 있으면 하나의 도구 후보입니다.

2. 읽기와 쓰기를 나눈다

조회만 하는 도구인지, DB를 바꾸는 도구인지 먼저 분류합니다. 쓰기 도구라면 입력값, 권한, 되돌림, 감사 로그를 더 엄격하게 봅니다.

3. 결과 모양을 정한다

모델이 답변에 쓸 수 있게 ok, total, items, error, truncated 같은 공통 필드를 정합니다.

새 조회 도구 스켈레톤 아래 모양은 원써치 도구 패턴을 줄인 예시입니다. 주석을 읽으며 어떤 약속이 필요한지 확인하세요. 
@function_tool
async def get_installation_risk_report(
    ctx: RunContextWrapper[Any],
    *,
    date_range: str = "today",
    limit: int = 100,
) -> dict[str, Any]:
    """
    설치 위험 리포트를 조회합니다.
    "오늘 설치 중 위험한 건", "내일 주의해야 할 설치" 같은 질문에 사용합니다.

    Args:
        date_range: "today" / "tomorrow" / "week" / "YYYY-MM-DD"
        limit: 최대 반환 건수. 너무 큰 결과를 막기 위해 서버에서 다시 제한합니다.
    """
    # 1) 입력값을 서버에서 다시 제한합니다.
    limit = max(1, min(int(limit or 100), 200))
    start, end, label = resolve_kst_date_range(date_range)

    # 2) 업무 목적에 맞는 읽기 쿼리만 실행합니다.
    result = await _execute_readonly_query(
        """
        SELECT contract_id, customer_name, status, installation_precautions
        FROM ...
        WHERE installation_schedule_date >= :start
          AND installation_schedule_date < :end
        LIMIT :limit
        """,
        {"start": start, "end": end, "limit": limit},
    )
    if not result["ok"]:
        return result

    # 3) 모델이 바로 요약할 수 있는 형태로 바꿔 반환합니다.
    items = [format_risk_item(row) for row in result["rows"]]
    return {
        "ok": True,
        "label": label,
        "total": len(items),
        "items": items,
        "truncated": len(items) >= limit,
    }

  • 입력 제한: 프론트나 모델이 보낸 값은 서버에서 다시 제한합니다. 특히 limit, 날짜, 상태값은 보수적으로 둡니다.

테스트 정상, 빈 결과, 잘못된 입력, 권한, timeout, 모델 allowlist를 확인했는가? 운영 중에만 실패 케이스가 드러납니다.

너무 큰 결과는 모델이 핵심을 놓치게 만듭니다. 서버가 먼저 요약하고, 필요한 범위만 넘기고, 잘린 결과인지 알려 주는 편이 안정적입니다.
14. Analytics에서 metric 근거 없이 그럴듯한 요약만 나왔다. 어떤 장치가 이를 막아야 하나? 보기를 선택하세요
  1. 근거가 빠진 분석 답변을 막는 출력 가드레일
  2. 브라우저 새로고침 방지 코드
  3. ChatKit 스크립트 주소 설정
  4. URL 끝의 슬래시를 정리하는 함수
A
정답: A
분석 답변은 근거가 핵심입니다. Analytics는 지표 코드나 fallback 근거 없이 그럴듯한 말만 하는 답변을 막는 출력 가드레일을 둡니다.
15. `run_readonly_sql`이 있는데도 전용 업무 도구를 계속 만드는 이유는? 보기를 선택하세요
  1. SQL을 절대 쓰지 않기 위해서
  2. 모델이 직접 DB를 학습하게 하려고
  3. 업무 규칙, 조회 제한, 결과 형식, 안전 기준을 서버 함수 안에 고정하기 위해서
  4. 프론트 코드를 줄이기 위해서
C
정답: C
전용 업무 도구는 “설치 브리핑”처럼 업무 의미를 담습니다. 단순 조회보다 고객, 계약, 주의사항, 체크리스트를 안정적인 구조로 돌려줄 수 있습니다.

  1. 사용자 메시지를 보낼 백엔드 ChatKit 접수창을 지정한다.
  2. DB 테이블 이름을 자동으로 고른다.

17. RequestContext(app=request.app, ...)를 만드는 이유로 가장 가까운 것은? 보기를 선택하세요
  1. 도구 실행 중 FastAPI app 같은 서버 문맥에 접근할 수 있게 하려고
  2. 사용자에게 DB 비밀번호를 보여 주려고
  3. 브라우저의 localStorage를 삭제하려고
  4. 모델 목록을 프론트에서 하드코딩하려고

18. 새 도구 함수를 만들었지만 Agent의 tools 목록에 넣지 않았다. 어떤 일이 생기는가? 보기를 선택하세요
  1. 모델이 자동으로 파일을 검색해 찾아낸다.
  2. 도구 설명 없이도 항상 호출된다.
  3. 서버에는 함수가 있어도 모델의 선택지에는 나타나지 않는다.
  4. 프론트 모델 선택 UI가 대신 실행한다.
C
정답: C
도구는 함수 작성, 도구 표시, Agent 등록이 모두 필요합니다. 특히 tools 목록은 모델에게 보여 주는 메뉴판 역할을 합니다.
19. _validate_readonly_sql이 세미콜론, UPDATE, DROP 등을 막는 이유는? 보기를 선택하세요
  1. SQL 결과를 더 예쁘게 정렬하려고
  2. 읽기 전용 도구가 실제로도 조회만 하도록 강제하려고
  3. 모델이 한국어를 못 쓰게 하려고
  4. 첨부파일 업로드 속도를 높이려고
B
정답: B
도구 이름이 읽기 전용이어도 모델이 만든 문자열은 서버가 검증해야 합니다. 여러 문장과 쓰기 키워드를 막아야 DB 변경 위험이 줄어듭니다.
20. 체크리스트 생성 코드의 ON CONFLICT ... DO NOTHING은 무엇을 지키는 장치인가? 보기를 선택하세요
  1. 이미 만들어진 체크 항목의 상태와 메모를 덮어쓰지 않게 한다.
  2. 모든 체크 항목을 매번 삭제하고 다시 만든다.
  3. 모델 allowlist를 자동으로 갱신한다.
  4. Prompt Studio 지침을 비운다.
A
정답: A
체크리스트 생성은 쓰기 도구입니다. 기존 작업자가 바꾼 상태와 메모를 보존해야 하므로 이미 있는 항목은 건너뛰는 방식이 안전합니다.

용어집 퀴즈

이 구조를 설명할 때 자주 섞이는 용어를 객관식으로 다시 확인합니다.

1. Agent 보기를 선택하세요
  1. 모델, 운영 지침, 설정, 도구 목록을 묶은 실행 단위
  2. 프론트 화면의 버튼 스타일
  3. DB 테이블을 자동 생성하는 기능
  4. 사용자가 업로드한 첨부파일 이름
A
정답: A
Agent는 “어떤 모델이, 어떤 지침을 보고, 어떤 도구를 사용할 수 있는가”를 묶는 단위입니다. 원써치 DB Chat도 이 단위로 실행됩니다.
2. Runner 보기를 선택하세요
  1. 모델 호출, 도구 실행, 결과 재입력, 최종 답변 생성을 진행하는 실행 엔진
  2. HTML을 예쁘게 접어 주는 CSS 기능
  3. DB에서 테이블 이름만 읽는 조회 함수
  4. 사용자 브라우저의 스크롤 관리자
A
정답: A
Runner는 단순 텍스트 스트리밍만 하지 않습니다. 모델이 도구를 고르면 서버 함수를 실행하고, 그 결과를 다시 모델에게 넣어 최종 답변까지 이어 줍니다.
3. Function tool 보기를 선택하세요
  1. 모델이 호출할 수 있도록 이름, 설명, 입력 형식이 공개된 서버 함수
  2. 사용자가 직접 브라우저에서 누르는 일반 버튼
  3. 모든 DB 권한을 자동으로 열어 주는 관리자 계정
  4. 프론트 화면만 바꾸는 디자인 파일
A
정답: A
Function tool은 일반 서버 함수를 모델이 요청할 수 있는 형태로 공개한 것입니다. 공개하지 않은 함수는 서버에 있어도 모델의 선택지가 아닙니다.
4. Tool schema 보기를 선택하세요
  1. 도구를 부를 때 어떤 입력값이 필요한지 알려 주는 약속
  2. 브라우저에서 글꼴 크기만 정하는 규칙
  3. DB 비밀번호를 보관하는 파일
  4. 추천 참고 글을 고르는 기준표
A
정답: A
Tool schema가 명확해야 모델이 날짜, 고객명, 범위 같은 입력값을 맞게 채울 수 있습니다. 입력 약속이 흐리면 잘못된 호출이 늘어납니다.
5. Prompt Studio 보기를 선택하세요
  1. 모델에게 어떤 기준으로 답하고 도구를 쓸지 알려 주는 운영 지침을 관리하는 곳
  2. 실제 업무 함수를 전부 저장하는 코드 폴더
  3. 고객 계약서를 직접 수정하는 화면
  4. 모델 허용 목록을 자동으로 구매하는 서비스
A
정답: A
도구 함수는 코드에 있고, Prompt Studio는 운영 지침을 관리합니다. “언제 어떤 도구를 써야 하는가”를 모델에게 알려 주는 역할입니다.
6. Allowlist 보기를 선택하세요
  1. 허용된 모델만 선택되게 하여 임의 모델 실행을 줄이는 장치
  2. 모든 사용자에게 관리자 권한을 주는 장치
  3. SQL 결과를 무제한으로 늘리는 설정
  4. 프론트 색상을 자동으로 고르는 기능
A
정답: A
Allowlist는 허용된 목록 안에서만 모델을 고르게 합니다. 프론트가 보낸 값을 백엔드가 다시 확인하기 때문에 임의 입력 위험이 줄어듭니다.
7. Read-only SQL 보기를 선택하세요
  1. 읽기만 허용하겠다는 의도가 실제 실행에서도 지켜지게 하려고
  2. SQL을 더 빠르게 외우게 하려고
  3. 프론트 화면을 자동으로 다시 그리려고
  4. 모델 허용 목록을 없애려고
A
정답: A
읽기 전용이라고 이름 붙였더라도 실제 실행 전에 위험한 문장과 키워드를 막아야 합니다. 그래야 “조회만 한다”는 약속이 실행 단계에서도 유지됩니다.
8. Agent-as-tool 보기를 선택하세요
  1. 작은 전문 Agent를 큰 Agent가 부를 수 있는 도구처럼 붙인 구조
  2. 프론트 버튼을 자동으로 번역하는 구조
  3. DB 테이블을 삭제하는 전용 명령
  4. 첨부파일을 이미지로만 바꾸는 기능
A
정답: A
Analytics는 한 함수가 모든 일을 하지 않습니다. 개념 파악, 지표 선택, 실행, 근거 정리를 맡는 작은 전문 Agent들을 도구처럼 연결합니다.
9. Guardrail 보기를 선택하세요
  1. 입력이나 출력이 위험하거나 근거가 부족할 때 막는 안전장치
  2. 답변 글자를 더 예쁘게 꾸미는 장식
  3. 모델을 더 비싸게 고르는 결제 옵션
  4. 브라우저 뒤로가기를 막는 기능
A
정답: A
Guardrail은 장식이 아닙니다. 쓰기 의도, 민감정보, 근거 없는 분석처럼 위험한 입력이나 출력을 잡아내는 안전장치입니다.
10. 성공 여부 반환값 보기를 선택하세요
  1. 모델이 도구 실행 성공과 실패를 쉽게 구분할 수 있다.
  2. DB 비밀번호가 자동으로 바뀐다.
  3. 프론트 디자인이 자동으로 새로워진다.
  4. 모든 오류가 사용자에게 숨겨진다.
A
정답: A
도구 결과에 성공 여부와 오류 이유가 있으면 모델이 사용자에게 정확히 안내할 수 있습니다. 실패를 숨기는 것보다 회복 가능한 정보로 돌려주는 것이 좋습니다.

적용 과제

새 도구를 하나 설계한다고 생각하고 아래 항목을 직접 채워 보세요.

  1. 사용자 질문 3개를 적고, 이 질문들이 같은 도구로 처리되어야 하는지 판단합니다.
  2. 도구 이름을 업무가 바로 보이게 정합니다. 예: 설치 위험 리포트 조회.
  3. 필수 인자, 선택 인자, 기본값, 날짜 기준을 정합니다.
  4. 성공했을 때와 실패했을 때 어떤 정보를 돌려줄지 각각 씁니다.
  5. 일반 조회 도구, 전용 업무 도구, 여러 단계 분석 흐름 중 어느 방식이 맞는지 결정합니다.
  6. 운영 지침에 들어갈 “언제 이 도구를 쓰는가” 문장을 2문장 이내로 씁니다.

핵심 요약

원써치 AI Chat의 툴은 모델에게 무제한 권한을 주는 장치가 아닙니다. 모델은 운영 지침과 도구 설명을 보고 “이 업무 도구를 실행해 달라”고 요청하고, 서버는 우리가 허용한 함수만 실행합니다. 그래서 새 기능은 이름, 입력값, 결과 형식, 실패 안내, 권한, 안전장치, 운영 지침까지 함께 설계할 때 안정적으로 동작합니다.

핵심은 AI가 직접 DB를 여는 것이 아니라, 원써치 서버가 허용한 업무 도구만 실행한다는 점입니다.
