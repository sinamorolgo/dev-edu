개발 이해 가이드 퀴즈

추천 참고 글

하네스를 제대로 이해할 때 먼저 읽기 좋은 글입니다.

개념의 큰 그림, 긴 작업 설계, 운영 인프라 관점을 빠르게 잡는 데 도움이 됩니다.

영문 개념 Harness engineering for coding agent users Martin Fowler. 하네스를 feedforward와 feedback 제어로 설명해 개념의 뼈대가 가장 선명합니다. 영문 설계 Harness design for long-running application development Anthropic. 플래너, 생성자, 평가자를 나눠 긴 작업을 끝내는 하네스 설계를 실제 사례로 보여줍니다. 한글 실전 하네스 엔지니어링으로 본 Deep Insight AWS 기술 블로그. 제어 환경, 권한, 컨텍스트, 로깅, 인프라 격리까지 한국어로 가장 직접적입니다. 한글 심화 장기 실행 애플리케이션 개발을 위한 하네스 설계 Anthropic 글의 한국어 번역. 생성자-평가자 루프와 스프린트 계약을 깊게 따라가기 좋습니다.

AI 개발 핵심 개념

하네스는 모델이 “답변”을 넘어 “일”을 하게 만드는 작업 환경입니다.

모델은 텍스트를 예측합니다. 에이전트는 도구를 쓰고, 상태를 기억하고, 실패를 관찰하고, 다시 시도하며 목표를 향해 갑니다. 이 차이를 만드는 모델 바깥의 코드, 규칙, 도구, 실행 환경, 검증 루프가 하네스입니다.

쉬운 정의

하네스는 AI에게 노트북, 업무 지침, 도구함, 작업 기록, 안전장치, 검사표를 마련해 주는 일입니다.

정확한 정의

AI 하네스는 모델을 제외한 실행 로직과 환경입니다. 프롬프트, 컨텍스트 주입, 도구 호출, 상태 저장, 샌드박스, 권한, 관측, 평가, 복구 루프를 묶어 모델 행동을 제어 가능하게 만듭니다.

AGENT = MODEL + HARNESS 모델이 아닌 거의 모든 것이 하네스입니다
MODEL 추론하고 응답을 생성하는 두뇌
+
HARNESS 도구, 상태, 규칙, 검증, 실행 환경
=
AGENT 목표를 향해 행동하는 시스템
C Context무엇을 알아야 하는가
T Tools무엇을 할 수 있는가
V Verify잘했는지 어떻게 아는가
S State어디까지 했는가
G Guard무엇을 막아야 하는가
O Observe무엇을 기록해야 하는가

왜 지금 중요한가

모델의 지능보다, 모델이 일하는 환경이 성능 차이를 만들기 시작했습니다.

최근 사례들은 같은 모델이라도 하네스를 어떻게 구성하느냐에 따라 결과가 크게 달라진다는 점을 반복해서 보여줍니다. 좋은 하네스는 모델의 약점을 가리는 장식이 아니라, 모델의 능력이 실제 업무로 전달되게 만드는 시스템입니다.

일의 단위

큰 목표를 작은 작업으로 쪼갭니다.

모델에게 “앱 만들어줘”라고만 하면 쉽게 산으로 갑니다. 하네스는 스펙, 작업 목록, 완료 기준, 인수인계 문서를 만들어 긴 작업을 견디게 합니다.

행동의 통로

도구를 안전하게 쓰게 합니다.

파일 읽기, 코드 실행, 브라우저 조작, DB 조회는 모두 권한과 실패 처리가 필요합니다. 하네스는 모델에게 손과 발을 주되, 위험한 행동은 제한합니다.

품질의 신호

잘못했을 때 바로 알게 합니다.

테스트, 타입 체크, 브라우저 검증, 로그, LLM 평가자, 사람 승인까지 모델이 읽을 수 있는 피드백으로 연결해야 수정 루프가 생깁니다.

오해 제거

하네스는 프롬프트 하나도 아니고, 벤치마크 하나도 아닙니다.

하네스라는 말이 넓어서 헷갈리기 쉽습니다. 핵심은 “모델 바깥에서 모델의 행동을 가능하게 하고, 제한하고, 관찰하는 구조”입니다.

오해 1. 하네스는 좋은 프롬프트다

프롬프트는 하네스의 부품일 수 있지만, 하네스 전체는 아닙니다. 실행 환경, 도구, 권한, 상태, 검증 루프가 빠지면 모델은 여전히 “말만 잘하는” 상태입니다.

정리. 프롬프트는 지시, 하네스는 환경

하네스는 지시를 실제 행동으로 바꾸는 구조입니다. “무엇을 하라”뿐 아니라 “어디서, 어떤 도구로, 어떤 기준을 통과해야 하는가”를 정합니다.

오해 2. 하네스는 평가 도구다

평가 하네스는 중요한 한 종류입니다. 하지만 에이전트 하네스는 평가뿐 아니라 도구 실행, 상태 보존, 컨텍스트 관리, 권한 제어까지 포함합니다.

정리. 평가는 센서 중 하나

테스트와 평가가 없으면 피드백이 약해집니다. 다만 하네스는 센서뿐 아니라 모델이 행동하는 작업장 전체를 가리킵니다.

오해 3. 좋은 모델이면 하네스가 필요 없다

모델이 좋아질수록 일부 보조 장치는 사라질 수 있습니다. 그러나 더 긴 작업, 더 위험한 도구, 더 많은 사용자로 확장되면 새로운 하네스 문제가 생깁니다.

정리. 하네스는 살아있는 시스템

하네스의 각 부품은 “모델이 아직 혼자 못하는 일”에 대한 가정입니다. 모델이 바뀌면 하네스도 줄이고, 바꾸고, 새로 붙여야 합니다.

구성요소

좋은 하네스는 여섯 가지 질문에 답합니다.

하네스를 “부품 목록”으로 외우기보다, 모델이 일을 끝내려면 무엇이 부족한지 질문으로 보면 기억하기 쉽습니다.

질문 하네스 부품 하는 일 예시
무엇을 알아야 하나? 컨텍스트, 메모리, 문서 지도 모델이 현재 작업과 도메인 규칙을 잊지 않게 합니다. AGENTS.md, 설계 문서, 작업 로그, 검색/RAG
무엇을 할 수 있나? 도구와 실행 환경 모델이 파일, 코드, 브라우저, API, 데이터베이스를 다루게 합니다. shell, browser, MCP, 내부 API, 코드 실행기
어디까지 맡길 것인가? 권한, 샌드박스, 승인 게이트 읽기/쓰기 범위와 위험 행동을 제한해 피해 반경을 줄입니다. 네트워크 allowlist, 파일 권한, 결제/삭제 전 사람 승인
어떻게 계속 이어가나? 상태, 체크포인트, 인수인계 긴 작업에서 진행 상황을 보존하고 다음 세션이 이어받게 합니다. feature list, progress file, git history, sprint contract
잘했는지 어떻게 아나? 센서와 평가 결과를 관찰하고 모델이 수정할 수 있는 신호로 바꿉니다. lint, tests, browser QA, logs, traces, LLM judge
실패하면 어떻게 고치나? 복구 루프와 래칫 같은 실수가 반복되면 문서, 훅, 테스트, 도구로 영구 반영합니다. 반복 실패 패턴을 규칙으로 추가, 차단 hook 생성

제어 루프

하네스 엔지니어링은 “실패를 시스템에 새기는” 반복 작업입니다.

Martin Fowler는 하네스를 사전에 방향을 주는 가이드와, 결과를 보고 수정하게 하는 센서의 조합으로 설명합니다. Mitchell Hashimoto식으로 말하면, 에이전트가 한 번 실수하면 다음에는 같은 실수를 못 하게 환경을 고치는 일입니다.

1

원하는 행동

예: PR을 만들기 전에 테스트를 돌리고, 실패 원인을 설명해야 한다.

2

가이드

규칙 문서, 스킬, 작업 순서, 성공 기준을 모델이 읽을 수 있게 둔다.

3

행동

모델이 도구를 호출하고, 파일을 바꾸고, 테스트를 실행한다.

4

센서

테스트, 타입 체크, 브라우저, 로그, 리뷰 에이전트가 결과를 읽는다.

5

하네스 수정

반복 실패는 새 규칙, 새 테스트, 새 도구, 새 권한 제한으로 바꾼다.

실제 글들이 공통으로 말하는 핵심은 “모델을 더 재촉하지 말고 환경을 고치라”입니다.

OpenAI Codex 사례

사람은 조향하고, 에이전트는 실행합니다.

OpenAI 글의 핵심은 사람이 직접 코드를 쓰는 대신, 에이전트가 읽고 검증할 수 있는 저장소, 문서, CI, 로그, 브라우저 검증 환경을 만든다는 점입니다.

R Repository as system of record중요 지식을 채팅이 아니라 저장소 문서와 실행 계획에 둡니다.
L Legibility for agentsUI, 로그, 메트릭을 에이전트가 직접 읽고 판단할 수 있게 만듭니다.
G Golden principles사람의 취향과 아키텍처 원칙을 린터, 규칙, 반복 정리 작업으로 고정합니다.
Anthropic 사례

긴 작업은 생성자와 평가자를 분리해야 합니다.

Anthropic 글의 핵심은 긴 자율 코딩에서 모델이 목표를 잃고 자기 결과를 과대평가한다는 점입니다. 그래서 계획, 생성, 평가를 나눠 품질 신호를 강하게 만듭니다.

P Planner짧은 요청을 제품 스펙과 작업 범위로 확장합니다.
G Generator합의된 작업 단위를 구현하고 자기 점검 후 넘깁니다.
E Evaluator실제 앱을 클릭하고, API와 DB 상태까지 확인해 통과 기준을 적용합니다.
Google Gemini 사례

하네스는 점점 관리형 인프라가 되고 있습니다.

Google의 Managed Agents 문서는 하네스를 API 한 번으로 띄우는 샌드박스, 파일, 웹 탐색, 도구 실행 환경으로 설명합니다. 이제 하네스는 앱 안의 작은 코드가 아니라 플랫폼 계층이기도 합니다.

S Sandbox격리된 Linux 환경에서 코드와 파일 작업을 수행합니다.
F FilesAGENTS.md, 스킬, 데이터를 파일로 정의해 버전 관리합니다.
H Human oversight민감한 워크플로우에서는 사람이 결과와 행동을 검토해야 합니다.
AWS Deep Insight 사례

프로덕션에서는 추론과 실행 인프라를 분리합니다.

AWS 글은 하네스를 안전한 운영 구조로 보여줍니다. 에이전트가 코드를 생성하더라도, 그 코드를 어디서 실행하고, 어떤 네트워크와 권한으로 격리할지까지 하네스 문제입니다.

I Isolation사용자별 실행 환경과 데이터 경로를 분리합니다.
N Network boundary민감 데이터가 퍼블릭 인터넷을 경유하지 않도록 제한합니다.
O Operations로깅, 모니터링, 세션 관리가 안정성의 핵심이 됩니다.

분류

AI 개발에서 하네스는 보통 세 층으로 나타납니다.

Agent harness

에이전트를 움직이는 운영 구조

모델이 도구를 쓰고, 상태를 저장하고, 작업을 분해하고, 검증 루프를 돌게 합니다. Claude Code, Codex, Cursor 같은 제품도 넓게 보면 하네스입니다.

Evaluation harness

모델과 앱을 같은 기준으로 평가하는 구조

테스트셋, 입력 생성, 모델 호출, 채점, 리포트를 묶습니다. 성능 비교나 회귀 방지에는 이 층이 필요합니다.

Product harness

실제 서비스에서 안전하게 일하게 하는 구조

권한, 승인, 감사 로그, 격리, 비용 제한, 사용자별 세션 관리까지 포함합니다. 데모를 프로덕션으로 올릴 때 중요해집니다.

적용 예시

고객 상담 AI를 만든다면, 하네스는 이렇게 보입니다.

코딩 에이전트가 아니어도 원리는 같습니다. 모델에게 회사 규정과 도구를 주고, 위험한 답변을 막고, 결과를 평가하고, 실패 사례를 다음 실행의 규칙으로 바꿉니다.

최소 하네스

처음부터 거창하게 만들 필요는 없습니다.

  • 상담 정책, 환불 규정, 금지 표현을 짧은 규칙 문서로 둡니다.
  • 주문 조회, 환불 접수, 상담 이관 API만 최소 권한으로 연결합니다.
  • 결제 취소, 개인정보 노출, 법적 답변은 사람 승인 게이트를 둡니다.
  • 대표 질문 50개와 실패 사례 20개로 작은 평가셋을 만듭니다.
  • 모든 도구 호출과 답변을 로그로 남기고, 반복 실패는 규칙이나 테스트로 승격합니다.

완료 기준

하네스가 있으면 “잘됨”을 구체적으로 말할 수 있습니다.

  • 정책 근거 없는 답변 비율이 줄었는가?
  • API 실패 시 사용자를 속이지 않고 이관하는가?
  • 민감 작업에서 승인 없이 실행하지 않는가?
  • 새 정책이 생겼을 때 문서와 평가셋이 함께 갱신되는가?
  • 운영자가 실패 원인을 로그에서 재현할 수 있는가?

확인 퀴즈

정의 복습에서 실제 설계 판단까지 단계적으로 풀어봅시다.

각 문제는 답을 고르면 정답과 해설이 표시됩니다. 틀려도 괜찮습니다. 해설을 읽으며 “모델 문제가 아니라 환경 문제로 바꿔 생각하는 법”을 익히는 것이 목표입니다.
