AI 개발 핵심 개념

하네스는 모델을 “쓸 수 있는 시스템”으로 만드는 실행 틀입니다.

AI 모델은 답을 만들 수 있지만, 혼자서는 문제를 고르고, 도구를 쓰고, 실패를 기록하고, 기준에 따라 통과 여부를 판단하지 못합니다. 그 주변 일을 맡는 코드와 규칙, 실행 환경이 하네스입니다.

쉬운 정의

모델에게 일을 시키고, 결과를 관찰하고, 필요한 기준으로 판정하는 “시험장 겸 작업장”입니다.

정확한 정의

AI 시스템에서 모델 자체를 제외한 실행 로직, 입력 구성, 도구 연결, 상태 관리, 평가, 제약, 로깅을 묶어 모델의 행동을 통제 가능하게 만드는 인프라입니다.

MODEL + HARNESS 모델 밖의 것들이 모델을 일하게 만듭니다
MODEL 답을 생성하는 두뇌
C Context문제, 문서, 프롬프트
T Tools검색, 코드, DB, API
G Guardrails권한, 제한, 금지 규칙

E Evals채점, 비교, 회귀 확인

하네스는 하나의 라이브러리 이름이 아니라, 모델 주변에 붙는 실행과 검증의 구조를 가리키는 말입니다.

왜 필요한가

좋은 모델을 고르는 문제에서, 믿을 수 있는 시스템을 만드는 문제로 바뀝니다.

모델만 바꾸면 품질이 좋아질 것 같지만, 실제 제품에서는 입력 품질, 도구 실패, 권한, 반복 실행, 평가 기준이 함께 품질을 만듭니다. 하네스는 그 변수들을 한곳에서 다룹니다.

반복 가능성

같은 조건으로 다시 실행합니다.

프롬프트, 테스트 데이터, 모델 설정, 채점 기준을 고정하면 “이번엔 왜 좋아졌지?”를 추적할 수 있습니다.

통제 가능성

모델이 할 수 있는 행동을 제한합니다.

어떤 도구를 쓸 수 있는지, 파일을 실제로 바꿔도 되는지, 실패하면 멈출지 다시 시도할지 정합니다.

판정 가능성

좋아졌는지 나빠졌는지 봅니다.

정답 비교, 규칙 기반 검사, LLM judge, 사람이 보는 리뷰를 연결해 품질 변화를 숫자와 사례로 남깁니다.

헷갈리는 말 구분

하네스는 모델도, 프롬프트도, 문제집도 아닙니다.

겉으로는 비슷해 보여도 역할이 다릅니다. 하네스는 “무엇을 실행하고 어떻게 판정할지”를 묶는 쪽에 가깝습니다.

용어 한 줄 설명 예시 하네스와의 관계
모델 입력을 받아 응답을 생성하는 AI 자체 GPT, Claude, Gemini, Llama 하네스가 실행하고 관찰하는 대상
프롬프트 모델에게 주는 지시문과 입력 형식 “다음 문서를 요약해줘” 하네스 안에 포함될 수 있는 부품
벤치마크 성능을 비교하기 위한 문제집 또는 데이터셋 100개 질문, 정답표, 테스트 케이스 하네스가 가져와 실행하는 재료
하네스 입력, 실행, 도구, 로그, 평가, 후속 조치를 표준화한 틀 테스트 러너, agent runtime, eval pipeline 모델을 제품이나 실험 안에서 다루는 구조
파이프라인 데이터와 작업이 흐르는 전체 처리 과정 수집, 검색, 생성, 검증, 저장 하네스보다 넓은 말로 쓰일 때가 많음

기본 구조

평가 하네스는 보통 이런 순서로 움직입니다.

핵심은 모델에게 그냥 물어보는 것이 아니라, 입력부터 결과 처리까지 한 번의 실험 단위로 고정하는 것입니다.

1. 입력 선택 테스트 데이터, 사용자 로그, 대표 시나리오를 고릅니다.
2. 실행 준비 프롬프트, 모델 설정, 도구 권한, 환경 변수를 맞춥니다.
3. 모델 호출 같은 조건으로 모델이나 에이전트를 반복 실행합니다.
4. 결과 채점 정답 비교, 규칙 검사, LLM judge, 사람 리뷰를 적용합니다.
5. 조치 결정 통과, 배포 차단, 회귀 알림, 실패 사례 저장으로 이어집니다.

세 가지 얼굴

AI 개발에서 하네스는 주로 세 맥락으로 쓰입니다.

Evaluation harness

모델을 같은 기준으로 평가하는 틀

모델 변경, 프롬프트 변경, 검색 방식 변경 후 품질이 좋아졌는지 확인합니다.

  • 테스트셋과 채점기 연결
  • 정확도, 비용, 지연시간 기록
  • 배포 전 회귀 테스트
Agent harness

모델을 에이전트처럼 움직이게 하는 틀

모델이 도구를 쓰고, 상태를 기억하고, 작업을 반복하며, 실패를 처리하게 만듭니다.

  • 파일 시스템, 웹, 코드 실행 연결
  • 메모리와 작업 상태 관리
  • 권한, 중단 조건, 재시도 규칙
Test harness

AI 기능이 제품 안에서 깨지지 않는지 보는 틀

AI 응답만 보는 것이 아니라 앱의 실제 흐름까지 함께 확인합니다.

  • 입력, 응답, 저장, 화면 표시 검증
  • API 실패와 예외 상황 테스트
  • CI에서 자동 실행

풀이 예시

“GPT와 Claude 중 어느 쪽이 고객 상담 답변을 잘하나?”를 본다고 해봅시다.

하네스 없이 보면

몇 개 질문을 직접 던져보고 “Claude가 더 자연스러운 것 같은데?”처럼 감으로 판단하기 쉽습니다. 질문이 바뀌면 결과도 바뀌고, 다음 주에 다시 비교해도 같은 결론인지 알기 어렵습니다.

질문 몇 개 직접 실행 느낌 비교 기록 부족 재현 어려움

하네스로 보면

대표 상담 100개, 금지 답변 규칙, 브랜드 톤 기준, 정답 근거 문서를 정합니다. 두 모델을 같은 입력으로 실행하고, 채점과 실패 사례를 저장합니다. 이제 “왜 더 나은지”를 설명할 수 있습니다.

100개 사례 동일 조건 자동 채점 실패 저장 배포 판단

확인 퀴즈

하네스인지 아닌지 구분해봅시다.

1. “100개 문제와 정답표”는 무엇에 가장 가까울까요?

답을 고르면 피드백이 표시됩니다.

2. “100개 문제를 두 모델에 넣고 점수 리포트를 만드는 코드”는?

답을 고르면 피드백이 표시됩니다.

3. 프롬프트 하나만 잘 써두면 하네스라고 부를 수 있을까요?

답을 고르면 피드백이 표시됩니다.

적용 체크리스트

내 AI 기능에 하네스가 있는지 보려면

  • 대표 입력과 실패 사례가 따로 모여 있는가?
  • 모델, 프롬프트, 도구 설정을 고정해서 다시 실행할 수 있는가?
  • 결과를 자동 또는 반자동으로 채점하는 기준이 있는가?
  • 비용, 지연시간, 오류, 도구 호출 로그가 남는가?
  • 점수가 나빠지면 배포를 막거나 알림을 보내는가?

핵심 요약

모델은 두뇌, 하네스는 일하는 환경입니다.

하네스는 모델 바깥에서 입력을 구성하고, 도구를 연결하고, 실행을 통제하고, 결과를 평가합니다. 그래서 AI 개발의 품질은 “어떤 모델을 쓰나”뿐 아니라 “어떤 하네스로 감싸나”에 크게 달려 있습니다.
