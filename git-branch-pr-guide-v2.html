개념 흐름 정리

Git 브랜치와 PR 올리기는 “안전하게 제안하고 합치는 흐름”입니다

브랜치, 커밋, 푸시, PR을 따로 외우면 헷갈립니다. 이 페이지는 변경사항이 어디에 놓이는지, 누가 언제 확인하는지, 마지막에 어떻게 main으로 합쳐지는지를 한 흐름으로 설명합니다.

흐름 보기 퀴즈로 확인
  • 1브랜치는 main을 어지럽히지 않는 작업 줄기입니다.
  • 2push는 내 컴퓨터의 작업 줄기를 원격 저장소에 올리는 일입니다.
  • 3PR은 “이 브랜치를 main에 합쳐도 될까요?”라고 검토를 요청하는 제안서입니다.

왜 필요한가

팀 작업의 핵심 문제는 “내 변경이 모두의 코드에 언제 들어가야 하는가”입니다

브랜치와 PR은 좋은 코드를 만드는 멋진 의식이 아니라, 실수와 충돌을 줄이기 위한 아주 현실적인 안전장치입니다.

안전

main을 바로 건드리지 않습니다

완성 전 작업은 별도 브랜치에 둡니다. 그래서 실험, 수정, 되돌리기를 해도 기본 줄기인 main은 비교적 안정적으로 유지됩니다.

공유

내 컴퓨터 밖으로 작업을 올립니다

push를 해야 팀원이 같은 변경사항을 볼 수 있습니다. push 전에는 대부분 내 컴퓨터 안의 기록일 뿐입니다.

검토

합치기 전에 맥락을 확인합니다

PR은 코드 차이, 설명, 질문, 리뷰, 승인 여부를 한 화면에 모읍니다. “합치기 전 대화 공간”이라고 보면 됩니다.

쉬운 정의와 정확한 정의

먼저 느낌으로 잡고, 그다음 기술적으로 정확히 잡습니다

초보자가 가장 많이 헷갈리는 지점은 branch와 PR을 같은 것으로 보는 것입니다. branch는 Git의 작업 줄기이고, PR은 GitHub 같은 협업 도구에서 여는 검토 요청입니다.

Branch

브랜치

기준 코드에서 잠시 갈라져 나와 내 작업을 담는 줄기입니다.

Git에서 브랜치는 특정 commit을 가리키는 이름입니다. 새 commit을 만들면 현재 브랜치가 그 commit을 가리키도록 이동합니다. 그래서 main과 다른 흐름의 변경 이력을 만들 수 있습니다.

Pull Request

PR

내 브랜치의 변경사항을 main에 합치자고 제안하는 검토 요청입니다.

Pull request는 한 브랜치의 변경사항을 다른 브랜치로 merge하자는 제안입니다. GitHub에서는 변경 차이, 설명, 리뷰 댓글, 승인, 충돌 상태를 함께 보여줍니다.

commit 작업 내용을 저장한 하나의 기록 지점입니다. “사진 한 장”처럼 나중에 비교하고 되돌아갈 수 있습니다.
push 내 컴퓨터의 commit과 branch를 원격 저장소에 올려 팀이 볼 수 있게 하는 동작입니다.
merge 한 브랜치의 변경 흐름을 다른 브랜치로 합치는 동작입니다. PR의 최종 목적은 보통 merge입니다.
base branch 변경사항이 들어갈 목적지입니다. 보통 main이나 develop입니다.
compare branch 내가 작업한 출발 브랜치입니다. PR 화면에서는 이 브랜치와 base branch의 차이를 보여줍니다.
review 팀원이 변경 의도, 코드 품질, 영향 범위를 확인하고 질문하거나 수정 요청을 남기는 과정입니다.

commit, push, PR, merge는 서로 다른 위치의 행동입니다

네 단어를 같은 “올리기”로 뭉뚱그리면 헷갈립니다. 어디에서 일어나는지와 결과물이 무엇인지로 구분하면 오래 기억됩니다.

commit

작업 저장

주로 내 컴퓨터의 현재 브랜치

변경사항을 담은 기록 지점

push 전에는 보통 볼 수 없습니다.

push

내 컴퓨터 → GitHub 같은 원격 저장소

볼 수 있습니다. 하지만 아직 main에 합쳐진 것은 아닙니다.

PR

검토 요청

GitHub, GitLab 같은 협업 화면

변경 제안서, 리뷰 대화, 승인 상태

볼 수 있고 댓글과 리뷰를 남길 수 있습니다.

merge

최종 합치기

PR 화면 또는 Git 명령

feature 변경이 main에 반영된 상태

main을 받는 모든 사람이 최종 변경을 받게 됩니다.

commit내 브랜치에 작업 기록을 남깁니다. push 전에는 보통 팀원이 볼 수 없습니다.
push내 기록을 원격 저장소에 공유합니다. 아직 main에 들어간 것은 아닙니다.
PR원격 브랜치를 main에 합치자고 제안하고 리뷰를 받습니다.
merge승인된 변경을 main에 최종 반영합니다.
예시와 비예시

비슷해 보이지만 핵심 조건이 다릅니다

예시는 개념의 중심을 보여주고, 비예시는 경계를 보여줍니다. 특히 PR은 “push했다”가 아니라 “merge를 제안했다”가 핵심입니다.

예시

좋은 브랜치와 PR 흐름

  • 브랜치: feature/login-error-message처럼 목적이 드러나는 이름으로 시작합니다.
  • commit: “로그인 실패 메시지 문구 수정”처럼 한 덩어리의 변경을 기록합니다.
  • PR: 무엇을 바꿨고 왜 바꿨는지, 확인 방법은 무엇인지 적어 리뷰를 요청합니다.
비예시

겉보기는 비슷하지만 다른 것

  • 수정만 한 파일: commit하지 않았다면 Git 기록으로 남지 않았습니다.
  • push만 한 브랜치: 팀원이 볼 수는 있지만 PR이 열리지 않았다면 검토 요청은 아직 아닙니다.
  • main 직접 수정: 브랜치와 리뷰 과정을 건너뛰므로 팀 작업에서는 위험할 수 있습니다.
풀이 예시

“회원가입 버튼 문구 수정”을 PR로 올려봅니다

작은 수정이어도 흐름은 같습니다. 중요한 것은 작업을 기록하고, 공유하고, 검토받고, 합치는 순서를 지키는 것입니다.

상황: 회원가입 버튼의 “가입” 문구를 “무료로 시작하기”로 바꾸고 싶습니다.

완료 기준은 세 가지입니다. 변경 이유가 PR 설명에 있고, 화면 확인 방법이 적혀 있고, 리뷰 후 main에 merge됩니다.

  1. 새 브랜치를 만듭니다 git switch -c feature/signup-button-copy
  2. 파일을 수정하고 상태를 확인합니다 git status로 어떤 파일이 바뀌었는지 봅니다.
  3. 변경을 commit합니다 git add . 후 git commit -m "Update signup button copy"로 기록합니다.
  4. 원격 저장소에 push합니다 git push -u origin feature/signup-button-copy로 GitHub에 브랜치를 올립니다.
  5. PR을 열고 리뷰를 받습니다 base는 main, compare는 내 feature 브랜치입니다. 승인 뒤 merge합니다.

적용 과제

이제 자기 작업에 바로 대입해봅니다

아래 빈칸을 실제 업무 상황으로 바꾸면 PR을 열기 전 생각할 내용이 정리됩니다.

내 작업 PR 초안

  • 브랜치 이름: feature/무엇을-바꾸는지
  • PR 제목: 사용자가 보게 될 변화나 해결한 문제
  • 변경 이유: 왜 지금 이 수정이 필요한지
  • 확인 방법: 어떤 화면에서 무엇을 확인하면 되는지
  • 리뷰 요청: 특히 봐줬으면 하는 파일이나 판단 지점

나중에 다시 볼 질문

  • 내 변경사항은 지금 local, remote, PR 화면 중 어디에 있나요?
  • 이 작업은 main에 바로 들어가도 안전한가요, 검토가 필요한가요?
  • 리뷰어가 이 PR의 목적과 확인 방법을 1분 안에 알 수 있나요?
  • merge 후에는 어떤 사용자가 어떤 변화를 보게 되나요?
핵심 요약

기억할 문장은 네 개면 충분합니다

브랜치

main에서 갈라진 작업 줄기입니다. 실험과 수정을 안전하게 담습니다.

commit

작업 내용을 저장한 기록 지점입니다. 나중에 비교하고 되돌릴 수 있습니다.

push

내 브랜치의 commit을 원격 저장소에 올려 팀이 볼 수 있게 합니다.

PR

브랜치를 main에 합치기 전에 설명하고 리뷰받는 제안서입니다.
